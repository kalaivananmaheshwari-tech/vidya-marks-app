## Validation decision and prerequisites applying to every row

**Can production validation safely proceed now? No determination is possible from local fixtures. Every row is REQUIRES AUTHORIZED PRODUCTION REVIEW.** Zero local violations demonstrate the diagnostic mechanism, not permission to validate production. Conditional validation is safe only after an authorized reviewer has:

1. Identified the exact production instance/schema and approved a maintenance/change window and accountable operator.
2. Captured a consistent backup and proven restoration to a separate environment, including record counts, original columns/IDs and application checks.
3. Reviewed the actual production catalog and read-only violation counts on a restored copy; reviewed additional semantic/null/role/legacy-allocation issues even where SQL permits them.
4. Resolved any violations using approved source evidence, never guessed mappings, deletion, ownership transfer, zero substitution or destructive retyping.
5. Rehearsed migration, validation locks/runtime and the application-version/backup recovery plan on that copy. Established lock/statement limits, monitoring and stop conditions.
6. Explicitly authorized each named constraint's production validation. A failed validation leaves it NOT VALID; stop and review rather than alter data to force success.

NOT VALID was chosen in additive migrations to enforce new/updated writes without scanning or rejecting possibly incompatible pre-existing rows at upgrade time. It is deliberate legacy preservation, not an exemption for new writes. Ordinary nullable foreign keys use PostgreSQL MATCH SIMPLE: a null referencing component is not a violation. CHECK expressions fail only when FALSE, not UNKNOWN. The diagnostic honors both semantics. The stronger permanent-mark-identity CHECK separately rejects missing identity fields. FKs prove relational scope, **not teacher role, assignment, entry ownership or current completion**; those remain backend business checks.
